Cloud Archive Storage in India: Glacier Alternatives, Retrieval Costs and Use Cases

Daya Shankar
September 3, 2026
16 min read
Quick Answer: Choose archive storage based on how quickly the data must be recovered, not only on the price per GB. AWS S3 Glacier Deep Archive and Azure Archive require a restore or rehydration process measured in hours. Google Cloud Archive keeps objects online with low-latency access but applies retrieval and minimum-duration charges. For recovery-critical data, keep a faster copy if the archive tier cannot meet the required RTO.

Cloud archive storage is designed for data that needs to be retained for a long time but accessed rarely.

The attractive part is easy to see: archive capacity can cost far less than hot object storage.

The harder question is:

How quickly can the data be recovered when it is actually needed?

That question matters for backups, compliance records, legal archives, historical datasets and cyber-recovery copies.

India’s data-centre footprint is also expanding. In August 2026, the Ministry of Electronics and Information Technology reported that installed data-centre capacity had grown from about 375 MW in 2020 to 1,575 MW in 2026.

At the same time, organizations are retaining larger volumes of application, backup, AI and compliance data for longer periods.

Archive strategy therefore needs to balance storage cost with recoverability.

If you first need to decide whether object storage is the right storage model, start with the Object Storage vs Block Storage vs File Storage guide.

Pricing and product note: Public documentation referenced in this guide was checked on 3 September 2026. Archive pricing, retrieval charges, region support and minimum-retention rules can change. Verify the provider's current documentation before moving production or compliance data.

What Is Cloud Archive Storage?

Cloud archive storage is a low-cost storage class intended for data that is rarely accessed but still needs to be retained.

Typical archive data includes:

  • Long-term backups
  • Financial records
  • Legal documents
  • Historical medical records
  • Audit evidence
  • Email archives
  • Media masters
  • Surveillance archives
  • Old application logs
  • Dormant AI datasets
  • Older model artifacts
  • Long-retention compliance data

Archive storage is usually cheaper than standard or hot storage because the provider assumes the data will be accessed infrequently.

In return, you may accept one or more trade-offs:

  • Higher retrieval charges
  • Longer restore times
  • Minimum storage durations
  • Early-deletion charges
  • Higher operation costs
  • Restore or rehydration workflows
  • Lower availability targets
  • Additional temporary-storage charges during recovery

Archive storage is therefore not simply “cheap object storage.”

It is a different access and recovery model.

The most important difference is whether the data remains directly accessible or must first be restored to an online state.

Start With Recovery Time, Not Storage Price

Archive capacity pricing is easy to compare.

Recovery behaviour is more important.

A useful sequence is:

Archive Selection Order
  1. Define the required Recovery Time Objective.
  2. Estimate how often archived data will be retrieved.
  3. Set the required retention period.
  4. Model retrieval, request, egress and early-deletion costs.
  5. Choose the archive class that fits those requirements.

For backup and disaster-recovery data, the Recovery Time Objective (RTO) describes how long the organization can tolerate before the service or required data is restored.

Archive retrieval time is only one part of that RTO, but it can become the limiting factor.

For example:

Recovery RequirementArchive Strategy to Consider
Seconds to minutesKeep an online or instant-access copy
Under 1 hourUse a class that supports immediate or high-priority access and verify throughput limits
Several hoursFlexible archive tiers may work
12 to 48 hoursDeep archive can become practical
Rare compliance retrievalOptimize more aggressively for retention cost

A seven-year-old compliance record may tolerate a multi-hour restore.

A production database backup needed within two hours probably should not exist only in a deep archive tier with a longer recovery window.

AWS S3 Glacier Deep Archive

AWS recommends S3 Glacier Deep Archive for data that is accessed less than once a year.

AWS currently documents:

  • Standard retrieval: typically within 12 hours
  • Bulk retrieval: typically within 48 hours
  • Minimum storage duration: 180 days

Objects in Deep Archive are not available for real-time access.

A restore request creates a temporary accessible copy while the original object remains in the Deep Archive class.

That means recovery planning needs to include more than retrieval time.

Potential costs can include:

  • Restore requests
  • Data retrieval
  • Temporary restored storage
  • Internet or inter-region transfer
  • Early deletion if the 180-day minimum is not met

Small Objects Need Extra Attention

AWS also documents 40 KB of additional metadata for every object stored in S3 Glacier Flexible Retrieval or S3 Glacier Deep Archive.

That consists of:

  • 32 KB charged at the relevant Glacier storage-class rate
  • 8 KB charged at S3 Standard rates

For a few large backup objects, this overhead is usually minor.

For millions of tiny logs, telemetry files or small objects, it can become more meaningful.

The number of objects is therefore part of archive economics.

Azure Archive Storage

Azure Blob Storage’s Archive tier is an offline tier.

A blob cannot be read or modified while it remains archived. It first needs to be rehydrated to an online tier.

Microsoft currently documents:

  • Standard priority: may take up to 15 hours for objects under 10 GB
  • High priority: may complete in under one hour for objects under 10 GB
  • Minimum archive duration: 180 days

High-priority rehydration costs more than Standard priority.

There is another practical detail for large recovery events.

Microsoft states that priority retrieval is subject to a 10 GiB/hour rehydration limit per storage account. Bulk restores can therefore take much longer than the “under one hour” headline for an individual small object.

This distinction matters during disaster recovery.

Restoring one 5 GB blob is different from restoring 50 TB of backup data.

Recovery planning point: Always test the restore volume you may need during a real incident. Per-object retrieval time does not automatically tell you how long a full environment recovery will take.

Google Cloud Archive Works Differently

Google Cloud Archive has a substantially different access model.

Google Cloud Storage classes, including Archive, remain online. Objects do not require a separate restore or rehydration process before they can be read.

Google currently documents:

  • Minimum storage duration: 365 days
  • Archive retrieval fee: $0.05/GiB
  • Applicable operation charges
  • Applicable network charges

This means Google Archive can provide low-latency object access even though it is intended for data accessed less than once a year.

The trade-off shifts from recovery delay toward retrieval economics and minimum retention.

If an archived object is deleted, replaced or moved before the 365-day minimum period is complete, early-deletion charges can apply.

This is why the phrase “Glacier alternative” needs care.

Google Cloud Archive and AWS Glacier Deep Archive can both serve long-term retention use cases, but their access models are different.

RTO Should Influence How Deep You Archive

The cheapest archive class may be the wrong class if its recovery process cannot meet the workload’s RTO.

Sophos’ 2026 State of Ransomware report found that 56% of attacks succeeded in encrypting data, while the average recovery cost reported by affected organizations reached $1.7 million.

Archive storage does not prevent ransomware on its own.

But a recovery design that has never tested its archive restore process can create additional delay during an incident.

A better design separates copies by recovery priority.

Fast Recovery Copy

Keep recent or business-critical recovery points in a storage tier that can meet the operational RTO.

Long-Term Archive

Move older recovery points and compliance data to lower-cost archive tiers when slower access is acceptable.

Independent Recovery Copy

Use immutability, separate credentials, accounts or regions where the threat model requires stronger recovery isolation.

The Cloud SLA Comparison Guide for India can help with availability planning, but backup recoverability should be tested separately from the provider’s service SLA.

Archive Storage Is Not the Same as Backup

This distinction is important.

Archive storage is a storage class or retention destination.

Backup is a recovery process that usually includes:

  • Which systems are copied
  • How frequently copies are created
  • How many versions are retained
  • Where those copies are stored
  • Whether copies are immutable
  • Who can delete them
  • How they are restored
  • How often restore testing is performed

Placing data in an archive class does not automatically create a complete backup strategy.

Likewise, keeping one archive copy of critical production data may not provide enough protection against:

  • Credential compromise
  • Accidental deletion
  • Corruption
  • Region failure
  • Malicious administrators
  • Ransomware
  • Provider-account compromise

Archive storage should be one component of a wider data-protection design.

Retrieval Cost Can Matter More Than Storage Cost

A low monthly storage rate is attractive when the data remains untouched.

The economics change during recovery.

A useful formula is:

Archive TCO: Storage + Requests + Retrieval + Temporary Restore Capacity + Egress + Early-Deletion Charges + Operational Recovery Cost

Consider three scenarios whenever you price archive storage:

  1. Normal year: Almost nothing is retrieved.
  2. Partial recovery: Around 10% of the archive is restored.
  3. Full recovery: The complete archive or backup set is retrieved.

The third scenario is usually the one that exposes whether the architecture is truly recoverable.

A service can be extremely cheap during eleven quiet months and still create a large bill or long delay during the month when recovery matters most.

Model Object Count, Not Just Terabytes

Ten terabytes stored as ten large objects behaves differently from ten terabytes stored as hundreds of millions of tiny objects.

Object count can affect:

  • PUT requests
  • LIST operations
  • Lifecycle transitions
  • Archive metadata overhead
  • Restore-request volume
  • Recovery coordination
  • Delete operations

This is especially relevant for:

  • Security logs
  • Telemetry
  • IoT events
  • RAG chunks
  • Application logs
  • Small image assets
  • Backup software that creates many objects

Where practical, some workloads can reduce archive overhead by aggregating many tiny files into larger archive objects.

That decision depends on how the data must later be searched and restored.

Which Data Belongs in Archive Storage?

Archive storage works best when future access is unlikely or predictable.

Strong Archive Candidates

Compliance records Legal archives Financial records Media masters Old backup generations Audit evidence Dormant AI datasets Historical logs

Data That Usually Needs Faster Storage

  • Active production databases
  • Frequently searched logs
  • Current backup recovery points
  • Frequently reused AI datasets
  • Active model artifacts
  • Shared application content
  • Data used by interactive analytics
  • Anything with an RTO shorter than the archive restore process

A simple rule is:

Old data is not automatically archive data. Archive data is data whose future access pattern fits an archive tier.

Archive Storage for AI and ML

AI workloads can generate large amounts of data that move through different temperature stages.

A simple lifecycle may look like:

Example AI Data Lifecycle
  • Active training dataset: Standard object storage or high-performance file storage
  • Current checkpoints: Faster object storage
  • Old experiment artifacts: Infrequent-access storage
  • Dormant datasets: Archive storage when future access is rare
  • Long-retention model and audit evidence: Archive storage where retention requirements permit

For GPU workloads, the cost of waiting for a large archived dataset can exceed the storage savings if expensive GPU resources remain idle during recovery.

That is why frequently reused training data should not automatically be moved to the coldest tier.

Data Location Still Matters

Archive data may remain stored for years.

That makes location, contractual terms and data governance more important, not less.

Before choosing a provider, verify:

  • Which region physically stores the archive
  • Whether replicas can leave that region
  • Where temporary restored copies are created
  • Whether cross-region replication is enabled
  • Which encryption and key-management options are available
  • Whether object lock or immutability is supported
  • How deletion and retention policies work
  • Whether the storage architecture meets customer or sector-specific requirements

For India-specific data-location considerations, see the Data Sovereignty and DPDP Cloud Guide.

Archive Storage Selection Checklist

Before moving production data to an archive tier, answer these questions:

  1. What is the required RTO for this data?
  2. How frequently is the data realistically retrieved?
  3. What percentage might need to be recovered during an incident?
  4. Does retrieval require a restore or rehydration step?
  5. What is the expected bulk-recovery throughput?
  6. Is there a minimum storage duration?
  7. What happens if data is deleted early?
  8. Is there a retrieval fee per GB or GiB?
  9. Are restore requests separately charged?
  10. Will a temporary restored copy create additional storage charges?
  11. What internet or cross-region egress charges apply?
  12. Does object count add metadata or request overhead?
  13. Can lifecycle policies move data automatically?
  14. Is immutability or object lock available?
  15. Where is the archived data physically stored?
  16. Has a full restore been tested?
  17. Is there a faster recovery copy for critical data?
  18. Does the provider’s support model fit a real recovery event?

FAQs

What is cloud archive storage?

Cloud archive storage is a low-cost storage class designed for data that is retained for long periods and accessed infrequently. It commonly trades lower storage cost for higher retrieval charges, minimum-retention periods or slower recovery workflows.

How long does AWS Glacier Deep Archive take to restore?

AWS currently states that S3 Glacier Deep Archive Standard retrieval typically completes within 12 hours, while Bulk retrieval typically completes within 48 hours. Very large restores or very large object counts can take longer.

How long does Azure Archive take to rehydrate?

Microsoft states that Standard-priority rehydration may take up to 15 hours for objects under 10 GB. High-priority requests may complete in under one hour for objects under 10 GB, although high priority costs more and bulk recovery is subject to account-level throughput limits.

Does Google Cloud Archive require rehydration?

No. Google Cloud Archive remains online and supports low-latency object access without a separate rehydration process. It currently has a 365-day minimum storage duration and a $0.05/GiB retrieval fee, plus applicable operation and network charges.

Is Glacier Deep Archive suitable for database backups?

It can be suitable for older backup generations when a multi-hour restore meets the recovery requirement. It should not be the only copy of a backup that must be restored faster than the archive retrieval window.

What is the biggest hidden cost in archive storage?

It depends on the workload. Retrieval fees, restore requests, temporary restored copies, early-deletion charges, egress and the operational impact of waiting for data can all become more important than the monthly storage rate during a recovery event.

What is the minimum storage duration for archive tiers?

AWS S3 Glacier Deep Archive currently uses a 180-day minimum. Azure Archive also uses 180 days. Google Cloud Archive uses 365 days. Other providers can use different minimums, so check the current storage-class terms before archiving data.

Is archive storage the same as backup?

No. Archive storage is a storage class or destination. A backup strategy also defines backup frequency, versions, retention, immutability, access controls, recovery procedures and restore testing.

Final Takeaway

The cheapest archive tier is not automatically the best archive tier.

Start with:

Recovery requirement → Retrieval frequency → Retention → Lifecycle cost → Storage class

Use deep archive when the data is genuinely cold and a multi-hour recovery window is acceptable.

Use online or faster tiers when the data may need to return quickly.

For backup and cyber-recovery workloads, do not discover the restore limitation during an incident. Test the amount of data you may actually need to recover, including the time, request volume and transfer cost involved.

The better archive strategy is not the one with the smallest monthly bill.

It is the one that keeps long-term storage economical without making recovery slower than the business can tolerate.
